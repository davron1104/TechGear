# Руководство по безопасности проекта TechGear (SECURITY.md)

Настоящий документ определяет обязательные правила, стандарты и механизмы обеспечения безопасности, которым должны следовать разработчик и AI-агент при реализации, изменении и развертывании интернет-магазина компьютерной техники и аксессуаров **TechGear**.

---

## 🎯 Назначение, область применения и приоритет

1. **Назначение:** Практическое руководство по безопасности для разработчиков и AI-агентов, предотвращающее появление уязвимостей и утечек данных на всех этапах разработки.
2. **Область применения:** Распространяется на весь исходный код проекта, включая Next.js Server Components, Server Actions, Route Handlers, клиентские компоненты, схемы валидации Zod, интеграции с базой данных Prisma/PostgreSQL, сторонними сервисами (Cloudinary, Telegram Bot API) и настройки CI/CD/хостинга.
3. **Приоритет:** Безопасность имеет абсолютный приоритет над удобством использования, скоростью разработки и упрощением кода. Меры безопасности не могут быть ослаблены или отключены ради ускорения разработки или быстрого исправления ошибок.

---

## 🔒 1. Контроль доступа (Access Control)

### Правило
Вся проверка прав доступа и сессий должна осуществляться строго на стороне сервера. Клиентский интерфейс является исключительно средством отображения и улучшения UX, и ему нельзя доверять принятие решений о доступе.

### Почему это важно
Злоумышленник может легко модифицировать клиентский код в браузере, обойти ограничения видимости элементов (скрытые кнопки, вкладки) или отправить прямой HTTP-запрос в Server Action или Route Handler в обход UI.

### Как это применяется в проекте
* **Ролевая модель:** В проекте предусмотрены две роли: `CUSTOMER` (покупатель) и `ADMIN` (администратор). Роли хранятся в БД в модели `User` и передаются в зашифрованной JWT-сессии Auth.js.
* **Серверная проверка:** Каждая операция, требующая авторизации, должна самостоятельно запрашивать сессию с помощью функции `auth()` на сервере Next.js и проверять роль пользователя:
  ```typescript
  const session = await auth();
  if (!session || session.user.role !== 'ADMIN') {
    return { success: false, error: 'Доступ запрещен' };
  }
  ```
* **Запрет доверия клиенту:** Запрещено принимать `userId` или `role` напрямую в параметрах запросов или Server Actions. Данные о текущем пользователе должны извлекаться исключительно из валидной сессии на сервере (`session.user.id`).
* **Принцип минимальных привилегий:** Покупатель (`CUSTOMER`) имеет доступ только к своим собственным данным. Он не может просматривать чужие заказы или чужие профили.

### Контроль доступа по разделам:
1. **Товары (Products):**
   * *Покупатели/Гости:* Только чтение активных товаров (`deletedAt: null`).
   * *Администраторы:* Полный доступ (CRUD) через Server Actions `createProduct`, `updateProduct`, `deleteProduct`.
2. **Категории (Categories):**
   * *Покупатели/Гости:* Только чтение категорий.
   * *Администраторы:* Полный доступ (CRUD) через Server Actions `createCategory`, `deleteCategory`.
3. **Заказы (Orders):**
   * *Гости:* Могут только создавать заказы. Доступа к истории заказов нет.
   * *Покупатели:* Могут создавать заказы, просматривать историю только своих заказов (где `userId` равен их ID из сессии). Покупатель может отменить собственный заказ через Server Action `cancelOrder` только в том случае, если заказ находится в статусе `NEW`.
   * *Администраторы:* Полный доступ на просмотр всех заказов и управление их статусами (подтверждение `confirmOrder`, отмена `cancelOrder`, перевод в `COMPLETED`).
4. **Профиль пользователя:**
   * Покупатель может просматривать и редактировать только свои данные (имя, фамилию, телефон, email) через `updateProfile`. Перед обновлением сервер проверяет, что изменяемый профиль принадлежит именно текущему авторизованному пользователю.
5. **Административная панель:**
   * Доступ к любым страницам под `/admin` блокируется на уровне Next.js Middleware (`src/middleware.ts`) путем проверки роли `ADMIN` в сессии. Дополнительно все административные Server Actions дублируют проверку прав на сервере.
6. **Загрузка изображений:**
   * Server Action `uploadProductImage` проверяет наличие сессии администратора перед обработкой и отправкой файла в Cloudinary.
7. **Операции изменения остатков:**
   * Списание товаров со склада выполняется строго сервером в рамках транзакции при переводе заказа в статус `CONFIRMED` администратором. Клиент никак не может напрямую изменять количество товара на складе.

## 🚫 2. Никогда не доверять клиенту (Never Trust the Client)

### Правило
Любые данные, поступающие от клиента (параметры запроса, тела Server Actions, FormData, заголовки, куки), считаются потенциально опасными и недостоверными.

### Почему это важно
Клиент может подменить идентификаторы, отправить невалидные количества, заниженные цены или попытаться изменить чужие данные, передав чужой ID.

### Как это применяется в проекте
* **Валидация критических полей:**
  * `productId`: Всегда проверяется на существование в БД перед добавлением в корзину или созданием заказа.
  * `quantity`: Должно быть строго положительным целым числом (`> 0`) и не превышать доступный остаток на складе (`Product.stock`).
  * `price` и `totalAmount`: **Клиент никогда не передает цену товара на сервер при покупке.** Цены извлекаются сервером напрямую из базы данных.
  * `orderId` и `userId`: Проверяются на принадлежность текущему пользователю перед выводом истории или отменой заказа.
  * `role` и `status` заказа: Никогда не принимаются от клиента для автоматического обновления. Статус заказа меняется только в результате выполнения логики на сервере (например, при подтверждении заказа администратором).

### Конкретный пример (Логика цен и остатков при оформлении заказа):
> [!IMPORTANT]
> **Недопустимый сценарий (Уязвимость):** Клиент передает массив товаров с ценами `[{ id: "123", price: 10 }]`, и сервер создает заказ на основе этих цен. Злоумышленник может купить видеокарту за 10 рублей.
>
> **Правильный сценарий (Безопасно):**
> 1. Клиент передает только список идентификаторов товаров и их количество: `[{ productId: "123", quantity: 2 }]`.
> 2. Сервер получает данные о товарах из БД по их `id` через Prisma.
> 3. Сервер проверяет, что товары не удалены (`deletedAt: null`).
> 4. Сервер берет актуальную цену (`price`) каждого товара напрямую из БД.
> 5. Сервер проверяет наличие: `stock >= quantity`.
> 6. Сервер самостоятельно рассчитывает стоимость каждой позиции и итоговую сумму заказа (`totalAmount`).
> 7. Сервер записывает актуальные цены и названия в `OrderItem` на момент оформления заказа.
> 8. При подтверждении заказа администратором сервер выполняет атомарное списание остатков со склада.

## 📝 3. Валидация входных данных (Input Validation)

### Правило
Все входящие параметры Server Actions и Route Handlers должны валидироваться на стороне сервера с использованием строгих схем. Валидация должна работать по принципу "белого списка" (whitelist).

### Почему это важно
Предотвращает передачу избыточных полей, инъекции некорректных типов данных, переполнение буфера и логические ошибки (например, отрицательные цены).

### Как это применяется в проекте
* **Использование Zod:** В проекте используется библиотека `Zod` для описания схем и парсинга данных.
* **Принцип Whitelist:** Метод `.parse()` или `.safeParse()` гарантирует, что в результирующий объект попадут только те поля, которые явно описаны в схеме. Любые лишние поля, присланные клиентом, будут проигнорированы или вызовут ошибку валидации.
* **Не полагаться на клиент:** HTML5-валидация и типы TypeScript существуют только для удобства пользователя и разработчика на этапе написания кода. На сервере все данные приходят как `unknown` и должны быть валидированы заново.

### Стандарты валидации полей:
* **Email:** Проверяется встроенным методом `z.string().email()`. Дополнительно проверяется уникальность email в БД при регистрации.
* **Строки:** Обязательное ограничение длины (например, имя пользователя: `.min(1).max(50)`, комментарий к заказу: `.max(500)`). Это защищает базу данных от переполнения.
* **Числа:** Проверка диапазонов (количество товара: `z.number().int().positive()`, цена товара: `z.number().positive()` или `z.string()` с последующей валидацией десятичного формата Decimal).
* **Enum:** Статусы заказов и роли пользователей должны строго соответствовать типам Prisma (`Role`, `OrderStatus`).
* **Данные профиля:** Имя, фамилия, телефон валидируются регулярными выражениями (например, телефон должен соответствовать формату РФ/СНГ).

## 🗄️ 4. Работа с базой данных (Database Security)

### Правило
Взаимодействие с PostgreSQL должно осуществляться через Prisma ORM. Запросы должны быть строго параметризованными. Все критические изменения (списание остатков, оформление заказов) должны проводиться в рамках транзакций.

### Почему это важно
Предотвращает SQL-инъекции и состояние гонки (race conditions), при котором несколько параллельных запросов могут списать один и тот же товар ниже нуля.

### Как это применяется в проекте
* **Параметризация:** Prisma ORM по умолчанию генерирует параметризованные SQL-запросы.
* **Запрет конкатенации:** Строго запрещено собирать строки SQL вручную с использованием пользовательского ввода. В случае острой необходимости использования сырого SQL (raw SQL) использовать исключительно безопасные методы `prisma.$queryRaw` или `prisma.$executeRaw` с передачей параметров в виде массива плейсхолдеров, а не интерполяцией строк.
* **Валидация перед записью:** Любые бизнес-проверки (наличие товара, права пользователя) должны выполняться до обращения к операциям записи в БД.
* **Транзакции и блокировки:** Операции оформления и подтверждения заказов должны использовать транзакции `prisma.$transaction`.

### Пример безопасного списания остатков (защита от race conditions):
```typescript
// src/services/stock-service.ts
const updated = await tx.product.updateMany({
  where: {
    id: item.productId,
    stock: { gte: item.quantity }, // Условие: остаток на складе должен быть больше или равен требуемому
    deletedAt: null
  },
  data: {
    stock: { decrement: item.quantity } // Атомарное уменьшение остатка
  }
});

if (updated.count === 0) {
  throw new Error(`Недостаточно товара на складе`);
}
```
*Использование `updateMany` с фильтром `stock: { gte: item.quantity }` гарантирует на уровне базы данных, что остаток никогда не уйдет в минус, даже если несколько администраторов одновременно подтвердят заказы.*

## 🔑 5. Аутентификация и сессии (Authentication & Session)

### Правило
Аутентификация должна базироваться на библиотеке `Auth.js (NextAuth.js v5)`. Пароли пользователей должны надежно хешироваться, а сессии — храниться в безопасных куках на стороне клиента.

### Почему это важно
Открытое хранение паролей приводит к компрометации аккаунтов при утечке БД. Хранение токенов в `localStorage` делает их уязвимыми перед XSS-атаками.

### Как это применяется в проекте
* **Хеширование паролей:** Для хеширования паролей используется безопасная библиотека криптографического хеширования (например, `bcryptjs` с достаточным количеством раундов/соли, рекомендованным для обеспечения безопасности). В базу данных записывается только хэш (`passwordHash`). Сравнение паролей при входе выполняется соответствующим методом (например, `bcrypt.compare`).
* **Безопасность кук (Cookies):** JWT-токен сессии сохраняется в куках с атрибутами:
  * `HttpOnly` (запрещает доступ к куке из JavaScript, предотвращая кражу при XSS);
  * `Secure` (передача куки только по HTTPS);
  * `SameSite=Lax` (защита от CSRF).
* **Запрет localStorage:** Строго запрещено сохранять чувствительные аутентификационные данные (JWT-токены, пароли, сессионные ключи) в `localStorage` или `sessionStorage` браузера. При этом хранение нечувствительного состояния клиента (такого как гостевая корзина товаров, описанная в `Architecture.md`) в локальном хранилище разрешено.
* **Безопасный Logout:** При выходе из системы сессия должна полностью уничтожаться как на клиенте, так и на сервере (вызовом метода `signOut()`), кука сессии должна очищаться.
* **Восстановление пароля:** 
  * Токены сброса пароля (`PasswordResetToken`) должны генерироваться на сервере с использованием криптографически стойкого генератора (`crypto.randomBytes`).
  * Токен имеет срок действия строго 1 час.
  * Токен является одноразовым и удаляется из БД сразу после успешного сброса пароля.
  * При запросе сброса пароля пользователю всегда выводится обобщенное сообщение: *"Ссылка отправлена, если email зарегистрирован"*, чтобы предотвратить перебор зарегистрированных адресов.

## 🛡️ 6. Управление секретами (Secrets Management)

### Правило
Все чувствительные данные (ключи API, пароли от БД, токены Telegram-ботов, секреты Cloudinary, настройки SMTP) должны храниться в переменных окружения и никогда не попадать в репозиторий Git.

### Почему это важно
Публикация секретов в публичных или даже приватных репозиториях Git приводит к мгновенной компрометации инфраструктуры автоматическими сканерами.

### Как это применяется в проекте
* **Локальные секреты:** Для локальной разработки используется файл `.env.local` (или `.env`).
* **Git Игнорирование:** Файлы `.env`, `.env.local`, `.env.production` должны быть обязательно внесены в `.gitignore`. В репозитории может храниться только демонстрационный файл `.env.example` без реальных значений.
* **Продакшн секреты:** Все ключи для рабочей среды настраиваются в панели управления хостинга (Vercel, Railway, Render и т.д.).
* **Специфичные секреты проекта:**
  * `DATABASE_URL` (строка подключения к PostgreSQL);
  * `NEXTAUTH_SECRET` (ключ шифрования сессий Auth.js);
  * `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` (для работы бота уведомлений);
  * `CLOUDINARY_URL`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` (для хранения изображений);
  * `SMTP_USER`, `SMTP_PASS` (для отправки писем сброса пароля).
* **Логирование:** Строго запрещено выводить значения секретов и переменных окружения в логи сервера (`console.log(process.env)`).
* **AI-агенты:** AI-агент не должен запрашивать у пользователя реальные секреты. При генерации примеров кода агент обязан использовать вымышленные заглушки (например, `process.env.TELEGRAM_BOT_TOKEN`).

## 🌐 7. Защита от XSS (Cross-Site Scripting)

### Правило
Все выводимые на клиенте данные должны проходить автоматическое экранирование. Использование небезопасных методов рендеринга HTML допускается только после предварительной очистки (санитизации) данных на сервере.

### Почему это важно
Позволяет избежать выполнения вредоносного JS-кода в браузере пользователя, который может быть внедрен злоумышленником через названия товаров, характеристики или комментарии к заказам.

### Как это применяется в проекте
* **Экранирование React:** JSX в React по умолчанию экранирует все строковые переменные перед выводом в DOM. Это поведение должно сохраняться.
* **dangerouslySetInnerHTML:** Использование свойства `dangerouslySetInnerHTML` строго запрещено для вывода сырых пользовательских данных. Вывод HTML-содержимого (такого как подробное описание товаров `Product.description`, заполняемое администратором через текстовый редактор) должен производиться только после предварительной очистки. Данные администратора не должны автоматически считаться безопасными.
* **Санитизация:** Любое HTML-содержимое, рендеримое через `dangerouslySetInnerHTML`, должно быть предварительно очищено (санитизировано) на стороне сервера с помощью библиотеки `isomorphic-dompurify` (или `dompurify`) во избежание XSS-уязвимостей через контент панели управления:
  ```typescript
  import DOMPurify from 'isomorphic-dompurify';
  
  const cleanHtml = DOMPurify.sanitize(product.description);
  ```

## 🍪 8. CSRF и файлы Cookie

### Правило
Проект должен быть защищен от межсайтовой подделки запросов (CSRF) на уровне архитектуры Next.js App Router и настроек сессионных кук.

### Почему это важно
Предотвращает выполнение несанкционированных действий (например, оформление заказа или изменение профиля) от имени авторизованного пользователя, если он перейдет на вредоносный сайт.

### Как это применяется в проекте
* **Server Actions:** Next.js Server Actions обладают встроенной защитой от CSRF. Фреймворк автоматически проверяет соответствие заголовков `Origin` и `Host` при вызове действий. Разработчик не должен отключать эти проверки.
* **SameSite Cookie Attribute:** Куки сессий Auth.js настраиваются с атрибутом `SameSite=Lax`. Это гарантирует, что браузер не будет отправлять куки авторизации при кросс-доменных запросах, инициированных сторонними ресурсами.
* **Route Handlers:** Для кастомных REST-эндпоинтов (Route Handlers) в `src/app/api/` проверка авторизации должна выполняться путем вызова `auth()` на сервере. Недопустимо доверять заголовкам авторизации, переданным в обход стандартного механизма сессионных кук, если эндпоинт предназначен только для внутреннего использования фронтендом.

## ⏳ 9. Ограничение частоты запросов (Rate Limiting)

### Правило
Критические публичные эндпоинты и Server Actions должны иметь ограничение на количество запросов в единицу времени для предотвращения атак типа "отказ в обслуживании" (DoS) и перебора паролей (Brute Force).

### Почему это важно
Защищает сервер от перегрузки, базу данных от исчерпания ресурсов, а также предотвращает финансовые потери от спам-рассылок (через SMTP) и перегрузку Telegram-бота уведомлений.

### Как это применяется в проекте
* **Точки ограничения:** Ограничение частоты запросов должно быть настроено для следующих операций:
  * Вход в аккаунт (`/login`, `/admin/login`);
  * Регистрация нового аккаунта (`/register`);
  * Запрос ссылки восстановления пароля;
  * Создание заказа (`createOrder`).
* **Реализация:** Ограничение может быть реализовано на уровне Next.js Middleware (например, с использованием распределенного хранилища Redis или локального in-memory хранилища в зависимости от архитектуры) либо на внешнем уровне (сетевые экраны, обратные прокси или API Gateways).

## 📤 10. Безопасность загрузки файлов (File Upload)

### Правило
Загрузка файлов должна осуществляться строго на стороне сервера (Server Action `uploadProductImage`) с жесткой валидацией размера, MIME-типа и расширения. Файлы должны направляться напрямую в безопасное облачное хранилище (Cloudinary).

### Почему это важно
Загрузка вредоносных исполняемых файлов (например, `.jsp`, `.exe`, `.php` под видом картинок) на сервер может привести к удаленному выполнению кода (RCE) и полной компрометации сервера.

### Как это применяется в проекте
* **Запрет прямого сохранения на диск:** Запрещено сохранять загруженные файлы в локальную файловую систему сервера (папку `public/` или временные папки). Файлы загружаются в буфер оперативной памяти и сразу передаются в Cloudinary.
* **Серверная валидация файла:**
  * **Размер:** На сервере должны проверяться лимиты размера файла (например, ограничение по умолчанию до 5 МБ или иное закрепленное в настройках значение). Файлы, превышающие лимит, должны отклоняться.
  * **MIME-тип:** Разрешается загрузка только безопасных графических типов (типичные примеры: `image/jpeg`, `image/png`, `image/webp`, `image/gif`). Проверка должна выполняться на сервере по содержимому файла (сигнатуре/magic numbers), а не только по переданному заголовку `Content-Type`.
  * **Расширение:** Разрешены только соответствующие безопасные расширения файлов (например, `.jpg`, `.jpeg`, `.png`, `.webp`, `.gif`).
* **Запрет доверия клиенту:** Атрибут `accept="image/*"` в HTML-теге `<input>` используется только для удобства выбора в операционной системе. Сервер обязан провести все проверки заново.

## 🪵 11. Ошибки и логирование (Errors & Logging)

### Правило
Сервер не должен передавать клиенту подробную техническую информацию об ошибках. Логирование на сервере не должно содержать конфиденциальные данные пользователей или системные секреты.

### Почему это важно
Утечка stack trace или структуры базы данных помогает злоумышленнику спланировать атаку. Запись паролей или токенов в системные логи делает их доступными для тех, кто имеет доступ к мониторингу серверов.

### Как это применяется в проекте
* **Маскирование ошибок:** При возникновении исключений в блоках `try-catch` системные детали (ошибки Prisma, сбои подключения PostgreSQL) записываются в логи сервера (`console.error`), а клиенту возвращается стандартизированное безопасное сообщение: *"Произошла внутренняя ошибка сервера. Пожалуйста, повторите попытку позже"*.
* **Конфиденциальность в логах:** В логах строго запрещено выводить:
  * Пароли пользователей в открытом или хешированном виде;
  * Токены сброса пароля (`PasswordResetToken`);
  * Сессионные куки и JWT;
  * Персональные данные покупателей (номера телефонов, email), если это не требуется для точечной отладки.

## 📦 12. Безопасность зависимостей (Dependency Security)

### Правило
Используемые сторонние библиотеки должны проходить регулярный аудит безопасности. Установка пакетов должна быть обоснованной.

### Почему это важно
Уязвимости в сторонних npm-пакетах (supply chain attacks) могут привести к компрометации всего приложения.

### Как это применяется в проекте
* **Версионирование:** Файл блокировки зависимостей (`package-lock.json` или `yarn.lock`) должен обязательно находиться под управлением Git и коммититься при любых изменениях.
* **Аудит уязвимостей:** В процессе разработки необходимо регулярно запускать команду `npm audit` для выявления известных уязвимостей в дереве зависимостей.
* **Минимизация пакетов:** Запрещено добавлять новые npm-пакеты без предварительного анализа их популярности, поддержки и истории безопасности. Если задачу можно решить простым стандартным кодом, следует избегать установки новой библиотеки.

## 🤖 13. Безопасность при работе с AI (AI Security Guidelines)

### Правило
AI-агент и разработчик должны критически относиться к сгенерированному коду. AI-агент обязан соблюдать правила неразглашения секретов и не должен ослаблять защитные механизмы приложения.

### Почему это важно
Модели AI могут генерировать код с типовыми уязвимостями (SQL-инъекции, отсутствие проверок авторизации) или предлагать небезопасные обходные пути ради решения сиюминутных ошибок сборки.

### Как это применяется в проекте
* **AI не источник истины:** Весь сгенерированный AI код, отвечающий за авторизацию, сессии, работу с БД или загрузку файлов, должен быть вручную проверен разработчиком на соответствие настоящему `SECURITY.md`.
* **Запрет передачи секретов в prompts:** Запрещено копировать реальные ключи доступа, пароли от баз данных или токены Telegram в диалог с AI. Используйте только вымышленные переменные среды (env placeholders).
* **Запрет ослабления защитных механизмов:** AI-агент не имеет права самостоятельно отключать валидацию данных, проверки ролей, политики CORS или менять уровни изоляции транзакций баз данных ради того, чтобы «прошли тесты» или «исправилась ошибка компиляции». Любое изменение защитных механизмов требует явного согласования с разработчиком.

## 🏁 14. Security Review перед завершением задачи (Чеклист)

Перед тем как пометить задачу завершенной или отправить код на слияние в основной репозиторий, разработчик и AI-агент обязаны пройти следующий чеклист:

- [ ] **Контроль доступа:** Все новые Server Actions и Route Handlers содержат серверную проверку авторизации (`auth()`) и роли (`ADMIN` / `CUSTOMER`).
- [ ] **Недоверие клиенту:** Параметры `price` и `totalAmount` не принимаются от клиента; они рассчитываются сервером на основе данных из БД.
- [ ] **Валидация данных:** Все входящие параметры проверены с помощью схем Zod (whitelist-подход, проверка типов, длины строк и диапазонов чисел).
- [ ] **Безопасность БД:** Запросы к БД осуществляются параметризованным способом через Prisma ORM. Нет ручной сборки SQL-строк конкатенацией.
- [ ] **Транзакции:** Критические операции изменения остатков на складе и создания заказов обернуты в транзакции Prisma с защитой от race conditions.
- [ ] **Аутентификация:** Пароли хешируются с использованием безопасных алгоритмов хеширования. Чувствительные токены авторизации хранятся только в `httpOnly` Secure куках (не в localStorage).
- [ ] **Сброс пароля:** Токены сброса пароля одноразовые, имеют срок действия 1 час и удаляются после использования.
- [ ] **Секреты:** В коде отсутствуют захардкоженные API-ключи, токены Telegram или реквизиты БД. Файл `.env.local` внесен в `.gitignore`.
- [ ] **Защита от XSS:** Данные экранируются React по умолчанию. Вывод HTML-описаний товаров санитизируется с помощью `isomorphic-dompurify`.
- [ ] **Безопасность файлов:** Загрузка картинок товаров валидируется на сервере по размеру (до 5 МБ), MIME-типу и расширению. Файлы отправляются в Cloudinary.
- [ ] **Логирование и ошибки:** В логах отсутствуют пароли и токены. Клиент получает только безопасные обобщенные сообщения об ошибках, без stack trace.
- [ ] **Зависимости:** package-lock.json закоммичен, уязвимости проверены через npm audit.
- [ ] **AI-безопасность:** В промптах отсутствуют реальные секреты, а сгенерированный AI код безопасности проверен вручную.
