# Инструкции по реализации Backend и Database (backend-rules.md)

Данные правила обязательны для выполнения при реализации бэкенд-логики, базы данных и интеграции сторонних сервисов в проекте **TechGear**.

---

## 1. Схема БД и Миграции (Prisma)

1. **Prisma Client Singleton**:
   - Для предотвращения переполнения пула соединений во время локальной разработки с hot-reload, инициализация Prisma Client должна выполняться через глобальный синглтон (например, с сохранением в `globalThis.prisma`).
2. **Управление изменениями схемы (Migrations)**:
   - Запрещено использовать `prisma db push` в качестве стандартного способа изменения схемы на постоянной основе.
   - Любое изменение в `schema.prisma` должно фиксироваться в репозитории вместе с автоматически сгенерированной миграцией `prisma migrate dev --name <migration_name>`.
3. **Наполнение данными (Seed)**:
   - Скрипт наполнения базы данных (`prisma/seed.ts`) должен быть воспроизводимым и не создавать дублирующие записи при повторном запуске.

## 2. Разработка Server Actions и Валидация

1. **Принцип нулевого доверия к клиенту**:
   - Всегда валидировать входящие параметры на сервере с помощью схем Zod (whitelist-подход).
   - Не использовать цены товаров (`price`) или итоговые суммы заказов (`totalAmount`), переданные с клиента. Данные значения должны запрашиваться и рассчитываться на сервере.
2. **Проверка авторизации и полномочий**:
   - Выполнять проверку сессии пользователя (`auth()`) и его роли (`ADMIN` / `CUSTOMER`) строго внутри тела Server Action.
3. **Безопасная обработка ошибок**:
   - Запрещено передавать сырые ошибки СУБД (Prisma), стек вызовов (stack trace) или сообщения внешних сервисов на клиент.
   - Всегда перехватывать ошибки (`try-catch`), логировать их на сервере (`console.error`), а клиенту возвращать понятное пользовательское сообщение.
4. **Формат ответа Server Action**:
   - Для действий, возвращающих бизнес-результат, использовать единый типизированный формат:
     ```typescript
     type ActionResponse<T> = 
       | { success: true; data: T }
       | { success: false; error: string; fields?: Record<string, string[]> };
     ```
   - Простые служебные действия, не возвращающие данных, могут возвращать `void` или бросать контролируемые ошибки, если это соответствует архитектуре.

## 3. Алгоритм слияния корзин (Cart Merge)

При авторизации пользователя гостевая Zustand-корзина должна переноситься в базу данных.
1. **Транзакционность**:
   - Операция слияния должна выполняться атомарно внутри транзакции Prisma.
2. **Логика слияния**:
   - Сверять гостевые элементы с БД-корзиной по `productId`.
   - Использовать актуальные данные товара из БД (актуальную цену, статус `deletedAt` и `stock`).
   - Исключать из слияния товары, которые помечены как удаленные (`deletedAt != null`).
   - Итоговое количество товара в БД не должно превышать его текущий доступный `stock`. Если суммарное количество превышает лимит, установить количество равным максимально доступному `stock`.
3. **Очистка состояния клиента**:
   - Очищать Zustand-стейт корзины на клиенте только после успешного завершения серверной операции слияния.

## 4. Управление запасами на складе (Stock) и Оформление заказа

1. **Создание заказа (createOrder)**:
   - Оформление заказа (записи `Order`, `OrderItem` и очистка корзины) должно происходить внутри интерактивной транзакции (`tx`).
   - При создании заказа проверяются актуальные цены и наличие товара на складе (`stock: { gte: quantity }`), но физического декремента запасов на этом шаге не происходит.
2. **Списание запасов со склада (Decrement)**:
   - Физическое списание (`decrement`) количества товара со склада происходит строго при смене статуса заказа из `NEW` в `CONFIRMED` администратором.
   - Операция списания должна быть атомарной и защищенной от overselling (race condition):
     ```typescript
     await tx.product.update({
       where: { id: productId, stock: { gte: quantity }, deletedAt: null },
       data: { stock: { decrement: quantity } }
     });
     ```

## 5. Мягкое удаление (Soft Delete)

1. **Правила мягкого удаления товаров**:
   - Модель `Product` должна содержать поле `deletedAt DateTime?`.
   - При запросе удаления товара необходимо проверить наличие связанных с ним исторических позиций заказов (`OrderItem`).
   - Если товар присутствует в оформленных заказах, вместо физического удаления выставляется дата `deletedAt`. Если связей с заказами нет, допускается физическое удаление товара.
2. **Ограничения в публичном каталоге и покупках**:
   - Товары с `deletedAt != null` должны быть скрыты из публичного каталога.
   - Запрещено добавлять товары с `deletedAt != null` в корзину или оформлять с ними новые заказы.
3. **Целостность заказов**:
   - Исторические записи `OrderItem` должны сохранять информацию о товаре (цену на момент покупки, название) независимо от дальнейшего мягкого или физического удаления `Product`.

## 6. Загрузка файлов (Cloudinary)

1. **Валидация файлов**:
   - Перед отправкой в облачное хранилище валидировать размер файла (до 5 МБ), MIME-тип и расширение файла (только безопасные изображения).
2. **Серверная передача**:
   - Загрузка картинок выполняется на стороне сервера через `Buffer`/поток, скрывая ключи API Cloudinary от клиента.

## 7. Сервис уведомлений в Telegram

1. **Изоляция уведомлений**:
   - Отправка уведомления о заказе не должна входить в транзакцию базы данных и не должна влиять на успешность оформления заказа пользователем.
2. **Асинхронный запуск**:
   - Уведомление должно запускаться асинхронно после завершения транзакции создания заказа.
   - Для предотвращения floating promises и unhandled rejection необходимо явно обрабатывать результат с помощью `.catch(err => console.error("Telegram notification error:", err))`.
3. **Безопасность**:
   - Любые ошибки доставки уведомления должны логироваться на сервере и не должны отображаться пользователю в интерфейсе.
