# PostgreSQL + Prisma ORM Best Practices & Patterns in TechGear

Данное руководство определяет стандарты и практические паттерны работы с базой данных PostgreSQL через Prisma ORM в приложении **TechGear** (Next.js App Router + Server Actions).

---

## 1. Prisma Schema & Миграции

1. **Регламент миграций**:
   - Все изменения схемы в `prisma/schema.prisma` фиксируются исключительно через миграции Prisma:
     ```bash
     npx prisma migrate dev --name <descriptive_migration_name>
     ```
   - Запрещено использовать `prisma db push` для постоянных изменений схемы в репозитории.
   - Имена миграций должны быть осмысленными и отражать суть изменения (например, `add_product_is_popular`, `rename_token_to_tokenhash`).

2. **Проверка деструктивных изменений**:
   - Перед применением миграций, содержащих `DROP COLUMN`, `DROP TABLE` или переименование полей, необходимо убедиться в сохранности пользовательских данных и корректности обратной совместимости.

3. **Prisma Client Singleton**:
   - Инициализация клиента всегда выполняется через синглтон (`src/lib/prisma.ts`) с драйвер-адаптером `@prisma/adapter-pg` для исключения утечек соединений при hot-reload.

## 2. Связи (Relations), Внешние Ключи и Каскады

1. **Политики ссылочной целостности**:
   - `onDelete: Cascade` используется для сущностей, не имеющих смысла без родителя:
     - `User -> Cart` (при удалении пользователя корзина удаляется).
     - `Cart -> CartItem` (при удалении корзины удаляются все ее элементы).
     - `Order -> OrderItem` (при удалении заказа удаляются его позиции).
     - `User -> PasswordResetToken` (токены сброса удаляются вместе с пользователем).
   - `onDelete: SetNull` используется для сохранения исторической целостности:
     - `User -> Order.userId` (если пользователь удален, оформленные заказы сохраняются для бухгалтерии/аналитики).
     - `Product -> OrderItem.productId` (если товар удален из каталога, строка в чеке заказа сохраняется).
   - `onDelete: Restrict` используется для защиты от случайного удаления структурных сущностей:
     - `Category -> Product` (нельзя удалить категорию, если в ней есть товары).

## 3. Индексы и Оптимизация Запросов (Предотвращение N+1)

1. **Композитные и точечные индексы**:
   - Поля, часто используемые в `WHERE` и `ORDER BY`, должны индексироваться:
     - `Product: @@index([categoryId, deletedAt])` — для фильтрации товаров по категории.
     - `Product: @@index([isPopular, deletedAt])` — для быстрых выборок популярных товаров.
     - `Order: @@index([userId, createdAt])` — для истории заказов пользователя.
   - Уникальные поля (`email`, `slug`, `tokenHash`, `@@unique([cartId, productId])`) автоматически индексируются PostgreSQL через B-Tree.

2. **Предотвращение проблемы N+1**:
   - Всегда использовать жадную загрузку связанных моделей через `include` или `select` внутри одного запроса вместо цикла запросов:
     ```typescript
     const cart = await prisma.cart.findUnique({
       where: { userId },
       include: {
         items: {
           include: { product: true },
         },
       },
     });
     ```

## 4. Интерактивные Транзакции и Конкурентность

1. **Атомарность операций (`prisma.$transaction`)**:
   - Все составные операции (создание заказа, слияние корзин, списание остатков, изменение нескольких таблиц) должны оборачиваться в `prisma.$transaction(async (tx) => { ... })`.
   - Если любая часть транзакции завершается ошибкой, все изменения автоматически откатываются.

2. **Защита от состояния гонки (Race Conditions) и Overselling**:
   - Проверка остатков на этапе создания заказа (`createOrder`):
     - Проверяется условие `product.stock >= quantity`, остатки в базе **не уменьшаются** (статус заказа `NEW`).
   - Физическое списание остатков на этапе подтверждения (`NEW -> CONFIRMED`):
     - Выполняется строго атомарный декремент с фильтром по доступному количеству:
       ```typescript
       await tx.product.update({
         where: { id: productId, stock: { gte: quantity }, deletedAt: null },
         data: { stock: { decrement: quantity } }
       });
       ```

## 5. Zero-Trust Безопасность для Server Actions

1. **Принцип нулевого доверия**:
   - Данные от клиента (цена товара, общая сумма заказа, наличие на складе) **не принимаются** как источник истины.
   - Сервер принимает только `productId` и `quantity`, а актуальные цены `price` и расчет `totalAmount` запрашивает и производит строго из базы данных.

2. **Валидация через Zod**:
   - Все входящие параметры Server Actions валидируются с помощью Zod-схем с проверкой граничных условий (`min(1)`, `max(...)`, `trim()`).

3. **Безопасная обработка ошибок**:
   - Ошибки базы данных логируются на сервере (`console.error`), а клиенту возвращается типизированный ответ `ActionResponse` с понятным сообщением без раскрытия структуры БД или stack trace:
     ```typescript
     type ActionResponse<T = void> =
       | { success: true; data: T }
       | { success: false; error: string; fields?: Record<string, string[]> };
     ```

## 6. Мягкое Удаление (Soft Delete) и Историческая Целостность

1. **Правило `deletedAt`**:
   - При удалении товара проверяется наличие связанных записей `OrderItem`:
     - Если товар уже заказывался (`OrderItem.count > 0`), выставляется `deletedAt: new Date()`.
     - Если связей нет, выполняется физический `delete`.
2. **Фильтрация в запросах**:
   - Все публичные выборки каталога, добавление в корзину и создание заказов обязаны содержать условие `deletedAt: null`.
3. **Снимки данных в заказах (`OrderItem`)**:
   - В момент создания заказа в `OrderItem` сохраняются `productName` и `price` на момент оформления покупки. Это гарантирует, что дальнейшее переименование, изменение цен или удаление товара не исказит историю заказов.
